## 1. 整体方案

该 monorepo 的错误处理围绕三个层次展开：
- **网络层**：基于 axios 的 `NetUtils`，通过请求/响应拦截器集中捕获异常，并回调应用注入的 `ErrorHandler`。
- **业务数据层**：所有网络调用统一返回 `{ code, message, data? }` 形式的 `Result<T>`，由调用方根据 `code` 判断成功或失败。
- **运行时校验层**：在框架内部对非法参数（如缺失 `viewId`、找不到 handler）直接 `throw new Error(...)`，作为开发期断言。

没有发现全局 `try/catch` 包裹、`Error` 子类体系、`panic/recover` 式恢复机制，也没有统一的错误码枚举；错误以“字符串消息 + 数字状态码”为主。

## 3. 架构与约定

### 3.1 网络错误：拦截器 + 回调模式
- `NetUtils.init(baseURL, loginUrl, loginAPI, errorHandler, tokenExpireTime)` 是入口。`errorHandler` 签名固定为 `(code: number, msg: string, type: 'request' | 'response') => void`，由应用层实现（demo 中用 antd `message.error` 弹出提示，并在 `code === 401` 时调用 `handleUnauthorized()` 跳转登录页）。
- **请求拦截器**：无 token 时调用 `errorHandler(401, '未找到授权Token', 'request')` 并 `Promise.reject(new Error('未找到授权Token'))`；拦截器本身抛错也走 `errorHandler(500, ...)`。
- **响应拦截器**：从 `error.response?.status` / `error.response?.data?.message` 提取 code/message 后回调 `errorHandler`，再 `Promise.reject(error)` 向上传递原始 axios 错误。
- `get/post` 方法只返回 `axios` 响应的 `.data`，即业务层的 `Result<T>`；因此上层调用者需要自行 `try/catch` 或 `.catch` 处理网络异常，或在业务逻辑中判断 `result.code`。

### 3.2 业务结果：统一 `Result<T>`
`interface.ts` 定义了 `Result<T>`：
```ts
interface Result<T extends any> {
  code: number;
  message: string;
  data?: T;
}
```
登录接口 `NetUtils.login` 即使 HTTP 200，也会根据 header 是否包含 token 等条件返回 `{ code: 400, message: '...' }` 这类业务失败结果，而非抛错。这体现了“网络异常抛错、业务失败返回 Result”的分层约定。

### 3.3 运行时断言：直接 throw
框架内部对“配置/参数错误”采用直接 `throw new Error(...)` 的方式，例如：
- `handlerBase.ts`：当 `viewId` 对应的 handler 不存在时抛出 `${viewId}对应的handler不存在`。
- `storeView.ts`：当 `viewId` 非字符串或为空时抛出 `未确认的viewId:${viewId}`。
这些错误不经过 `ErrorHandler`，属于开发期/启动期不可恢复的编程错误。

### 3.4 未授权流程
`tokenUtils.ts` 提供 `clearTokenAndJumpToLogin(loginUrl)`，在 `checkToken` 无 token 时清空本地存储并 `window.location.replace` 到登录页；`NetUtils` 的 request 拦截器在未找到 token 时也触发此流程（通过 `errorHandler` 暴露给应用层）。这是唯一涉及页面跳转的错误路径。

## 4. 约定与约束

- **网络错误必须经拦截器回调**：所有 axios 请求都会进入拦截器，业务代码不应绕过 `NetUtils.get/post` 直接调用 axios，否则无法获得统一的 token 注入与错误回调。
- **业务 API 返回值统一为 `Result<T>`**：调用方应检查 `result.code` 是否为成功态，而不是依赖 try/catch 捕获业务失败。
- **401 未授权统一处理**：应用层在 `errorHandler` 中识别 `code === 401` 并调用 `NetUtils.handleUnauthorized()`，避免各模块重复实现跳转逻辑。
- **运行时参数校验使用 throw**：对 `viewId` 等核心参数的空值校验直接抛错，表明这些是“绝不应该发生”的编程错误，而非可恢复的业务异常。
- **无全局错误边界**：React 组件层未发现 `componentDidCatch` 或 `ErrorBoundary`；UI 层错误主要依赖 antd 的 `message.error` 展示。
- **无自定义 Error 子类**：全仓未发现 `class XxxError extends Error` 或统一错误码枚举，错误信息以模板字符串形式嵌入抛错语句中。

## 5. 总结

该仓库的错误处理采取“分层清晰但轻量”的策略：网络异常集中在 axios 拦截器并通过回调上报，业务失败通过 `Result<T>.code` 表达，框架内部对非法参数直接抛错。它没有引入复杂的错误类型体系或全局错误边界，适合企业级后台系统中“以网络拦截为核心、业务层自判结果码”的常见模式。
