## 2. A 类：设计稿与现实不符（须回写文档）

### A1 【最高优先·阻塞 M2 收尾】§5.5.2 的预览宿主示例代码无法运行

设计稿写：

```534:535:docs/design/可视化代码编辑器中台开发计划.md
const { ViewClass, DataClass, HandlerClass } =
  await import(/* @vite-ignore */ '/@fs/' + params.get('page'));
```

但 `index.tsx` **只有默认导出**，无任何具名导出：

```9:9:apps/demo/src/pages/base/table/index.tsx
export default DemoTablePage;
```

`ViewClass` 等三个变量恒为 `undefined`，照抄必崩。且与设计稿 §5.2.1"解析三个类的实际导入来源"自相矛盾。

**实际实现更优**（渲染页面默认导出，无需知道任何类名）：

```92:107:packages/studio/preview/src/main.tsx
  const Page = (mod.default ?? mod.Page) as React.ComponentType | undefined;
```

**动作**：§5.5.2 整段替换为 `mod.default` 写法，并补上它更好的理由（预览形态 = 真实应用形态）。

### A2 【阻塞 M2】§5.5.2 的 alias 只写 `@jl/framework` 会全线编译失败

设计稿只写 `{ '@jl/framework': frameworkSrc, ...profile.aliases }`。但框架 `src/index.ts` 通篇用裸别名自引用（`@view/`、`@ctrl/`、`@utils/`…，共 7 个，定义在 `packages/framework/alias.ts:11-21`），Vite 不对子文件 import 走包名解析。

**实际实现已正确处理**：

```56:59:packages/studio/preview/vite.config.ts
    alias: {
      '@jl/framework': frameworkSrc,
      ...getFrameworkAliases(),
    },
```

**动作**：设计稿补写"必须叠加 `getFrameworkAliases()`"，并说明 `ProjectProfile.overrides.frameworkAliasTo` 这个**单值字段表达不了 7 个别名**，应改为 `frameworkAliases?: Record<string,string>`。

### A3 【阻塞 M2】`import.meta.env` 问题设计稿完全未覆盖

预览宿主跑在自己的 Vite 里，目标工程的 `.env` **不会被加载**，`import.meta.env.VITE_BASE_URL` 会变 `undefined`，`NetUtils` 直接失去 baseURL。

实际实现为此专门写了一个 Vite 插件做源码改写（`preview/vite.config.ts:14-30`），再由宿主从 URL 参数注回（`preview/src/main.tsx:31-36`）——这是整个预览方案最容易踩的坑，设计稿一字未提。

**动作**：补进 §5.5.2 与 §12.2 测试矩阵。

### A4 【设计稿自相矛盾】`.bak` 落点 vs "绝不往目标工程写文件"

- §4.3：备份 `<name>.bak` —— 落在**目标源码目录内**；
- §5.1.3：「绝不往目标工程里写 `.studio/` 之类目录（避免污染 git）」。

两条互斥。**当前的缓解是加 `.gitignore` 的 `*.bak`**，属于事后补救——文件仍落在源码树里，且 `*.bak` 是全仓库规则，会误伤任何正当的 `.bak` 文件。

**动作**：二选一并写进设计稿——(a) 明确"只保留 `.gitignore` 缓解"；(b) `.bak` 改写到 `UserConfigDir`（更干净，但会失去"与源文件同目录可见性"）。

### A5 【影响验收】页面数量错：设计稿 3 处写"9 个页面候选"

实际 `apps/demo/src/pages/**/index.tsx` 共 **8 个**（`pages/index`、`home`、`base/{drawer,form,modal,tab,table}`、`composite/formAndTable`）。影响 §9 步骤 4、§11 M0 退出条件、§14 验收剧本。

### A6 【细节】§5.5.1 方案 A 的 dev 端口

设计稿写 `localhost:7000`。7000 是 **desktop 分支**的值；浏览器模式是 `env.VITE_SERVER_PORT || 3000`（`vite.config.ts:59`）。且**实际探测把它取成了 3000**（见 §1.3 末），说明探测逻辑读的是 `.env.production`。

### A7 【文档已失效】§2.7 称 `renderProbe.ts` 可复用为元素探针挂载点

实际 `packages/framework/src/utils/renderProbe.ts`（137 行）是 **React 渲染计时/重渲染计数诊断工具**（`localStorage 'renderProbe'` 开关 + `console.debug`），与 DOM 标记**毫无关系**，且不进 `index.ts` 公共导出。设计稿"复用并扩展"的判断不成立——这是**新建**，不是复用。

### A8 【未做但被写成已做】§2.1 workspace glob 与 §8 工程组织

- §2.1 称只有 `apps/*`、`packages/*` 两个 glob；实际 `pnpm-workspace.yaml:7` 已加 `packages/studio/*`。
- §8 称顶层有 `packages/studio/package.json`（name `@jl/studio`）作为 workspace 锚点；**该文件不存在**。三个子包各自是独立 workspace 成员（`@jl/studio-web` / `@jl/studio-analyzer` / `@jl/studio-preview`）。
- 后果验证：根 `package.json` 的 `build`/`dev` 走 `turbo run` 且 `turbo.json` 无 filter，`turbo run build` **会连带构建 studio-web 与 studio-preview**；根 `pnpm dev` 会同时拉起 demo(7000) + preview(7099) + studio-web。设计稿 §8 预言的"避免 turbo 误跑"并未实现。
- 根脚本已加 `dev:studio` / `build:studio` / `server:studio`，但 `pnpm --filter @jl/studio meta:gen`（设计稿 §5.3.3）**无从执行**。

**动作**：§2.1/§8 需整体重写为实际结构，并明确 turbo 纳管现状。

### A9 主题色空间被混写（实测证据）

本轮 git diff 显示 `packages/framework/src/ui/styles/theme.css` 出现过一次改动：`--foreground: oklch(0.145 0 0)` → `#1b3a57`。这恰好暴露了设计稿 §5.7 的核心问题：

- 框架全站 token 是 **OKLCH**，而这里被写成 **HEX**——同一份 token 表里混了两个色空间；
- 设计稿 §4.4 选定 `culori` 做 OKLCH⇄sRGB⇄HEX，但**未安装**（`analyzer/package.json` 只有 `typescript`）；
- 因此 §5.7.4 的"对比度校验（4.5:1）"**在物理上无法计算**（跨色空间），§5.7.2 的"HEX/OKLCH 三输入联动"也无从实现。

> 该改动检查期间已被回滚（`theme.css.bak` 现已不存在，`theme.css` 回到 HEAD 状态），但这说明写回链路**确实能穿透到框架包源码**——见 B2。

## 3. B 类：违反设计稿自定规则（P0，须改代码）

> 设计稿把这些写成硬规则/安全承诺，实现未兑现。按风险排序。

### P0-1 `/api/open` 可执行任意命令 —— 局域网模式下等同于远程 RCE

- `server/api.go:734-766` 接受请求体里的 `command`；
- `server/editor.go:105-106`：**请求体自带模板时优先使用**，绕过 `knownEditors` 白名单；
- `server/editor.go:142-149` + `163-180`：模板按空白切分后，Windows 上无条件 `cmd /c` 拼接执行。

设计稿 §10.1 承诺「外部进程仅白名单：`code -g`/`pnpm`/`node`，全部参数数组化，不拼 shell 字符串」。实际是"请求体给什么就执行什么"。且前端 `web/src/store/studio.ts:114` 从 `localStorage['studio.editorCommand']` 取值并入参——**任意网页脚本可先写 localStorage 再触发**。

**动作**：删除请求体模板入口；命令只能取服务端白名单；`cmd /c` 改为显式 argv；执行前弹确认。

### P0-2 `blockedDir` 定义了但从未使用 → `node_modules`/`dist`/`.git` 可写

`server/util.go:103-106` 定义了黑名单，全仓库 grep 仅命中定义处。`Apply`（`edit.go:202`）与 `Switch`（`edit.go:296-323`，**连扩展名都不查**）只校验扩展名。设计稿 §10.1 承诺拒绝这些目录。

### P0-3 路径白名单放宽到整个框架包

`server/project.go:40-52` 的 `AllowedRoots()` 除项目根外，还加入 `Dir(Dir(FrameworkSrc))`（= 整个 `packages/framework`）与每个主题文件的 `Dir`。

后果已实测发生：一次主题编辑就把 `.bak` 写进了 `packages/framework/src/ui/styles/`（见 A9）。设计稿 §5.7.1 只授权"改 `theme.css` 的 token 值"。

**动作**：白名单精确到**文件**而非目录。

### P0-4 `.env` 明文落盘 + 明文下发浏览器

`server/project.go:20-21` 的 `Env`/`EnvSources` 是持久化字段，被写进 `%APPDATA%\frontark-studio\projects.json`，并由 `api.go:777-788`（`/api/preview`）与 `api.go:214`（`GET /api/projects/{id}`）原样返回。全仓库无 `mask` 逻辑。

> 实测补充：当前 `projects.json` 里**没有** `env` 字段（`omitempty` 未被填充），所以尚未造成实际泄露——但代码路径已具备泄露能力，一旦探测填入即中招。设计稿 §10.1「不落盘敏感值」「只读 + 值掩码」均未实现。

### P0-5 静态资源与 SSE 被纳入鉴权 → 局域网模式不可用

`main.go:110` 把鉴权套在**全部**路由（含 SPA 静态托管）外层。后果：

- 局域网模式浏览器打开首页即 401（设计稿只要求保护 `/api/*`）；
- **`EventSource` API 无法设置 `Authorization` 头** → SSE 永久不可用。设计稿 §10.1 与 §6.3 完全没考虑这个约束。

**动作**：静态资源免鉴权；SSE 改用 `?token=` query 或 cookie。

### P0-6 无请求体大小限制 / 无 HTTP 超时（DoS）

`api.go:66-78` 的 `decodeBody` 未包 `http.MaxBytesReader`（全仓库 0 命中）；`main.go:122` 用包级 `http.ListenAndServe`，无 `ReadHeaderTimeout` 等（无 `http.Server` 实例）。

### P0-7 主题实时预览**实际是坏的**

`web/src/store/studio.ts:329`：`const token = k.split('|')[1]`，而草稿 key 格式是 `${file}|${selector}|${token}`（`ThemePanel.tsx:95`）——`[1]` 取到的是 **selector**，生成 `--:root: oklch(...)` 这种非法变量名，浏览器直接丢弃。

**功能看似已实现，实则完全无效**——这是最容易误判为"已完成"的一处。

### P0-8 主题 token 重复时只改第一处 → 幽灵值

`analyzer/src/theme.mjs:37-59` 的 `parseTheme` 用 `/g` 会返回同一 block 内**重复的同名 token 多条记录**；而 `theme.mjs:149-151` 的 `planThemeSet` 用**不带 `g`** 的 `re.exec` **只取第一个**。结果：UI 显示两条、只能改第一条，第二条变成无人能改的幽灵值。

（另：`theme.mjs:52` 的 `start: start + rawValue.length - rawValue.trimEnd().length * 0` 里 `* 0` 是无意义表达式，作者意图已丢失。）

### P0-9 无 `anchor.hash` → 漂移检测不存在

设计稿 §5.2.2 明确要求 `SourceAnchor.hash: "该区间文本的 sha1（apply 时校验漂移）"`，但 `analyze.mjs:220-234` 的 `anchorOf` 产出 `{file,start,end,line,column,endLine,endColumn}`——**没有 hash**。`fsutil.mjs:10` 定义了 `sha1` 但**全项目零调用**。

即 §5.4.1 步骤③"校验 nodeId 与 anchor 未漂移"完全没有实现。当前漂移检测实际只靠 Go 侧的内容哈希兜底。

### P0-10 引号风格判定用"附近多数派"而非原字面量

`fsutil.mjs:23-52` 的 `detectQuote` 取 **±400 字符内的多数派引号**，而不是**被替换区间自身**的引号；`edit.mjs:170` 的 `serializeScalar` 只传位置不传原字面量。结果：一个双引号属性可能被改写成单引号——直接违反设计稿 §5.4.2 的"保留引号风格"。另 `templates.mjs:40,50` 硬编码 `JSON.stringify` 双引号。

### P0-11 对象展开/重复属性未按规则降级 source-only

设计稿 §5.2.2 原文：「遇到对象展开/计算属性/重复属性时，必须评估是否覆盖目标字段；无法确定覆盖顺序 → 该字段关闭写入，降级 `source-only`」。实际：

- `analyze.mjs:72-77` 的 `findProp` 返回**第一个**匹配属性，而 JS 语义是**最后一个生效**；
- 含 spread 的对象，其 `id`/`type` **仍被提取**，未降级（`analyze.mjs:535-538`）——正是规则要求降级的场景；
- 后果：`viewMembers[].id` 错 → `ST001` 重复检查、`rename` 的 `declaredId` 全跟着错。

## 5. C 类：设计稿需补充的关键空白

以下问题设计稿完全没有涉及，但实现必须回答，建议补进相应章节：

1. **偏移单位约定**（建议补 §5.4.2）：Node 与 Go 之间的字符偏移是 **UTF-16 code unit**，BOM 计入 U+FEFF。Go 侧已用 `utf16.Encode/Decode` 对齐（`server/edit.go:137-160`），**两侧口径一致，这是当前实现的亮点**——但设计稿没写，未来任何人改动任一侧都会踩坑。
2. **指纹算法定稿**：设计稿 §1.3/§4.3 写 "mtime + 内容 sha256 双校验"，实现是**仅 SHA-1、无 mtime、无 ETag**（`util.go:38-41`）。建议直接改文档为"内容哈希（SHA-1）"并说明为何放弃 mtime（mtime 不可靠）——比补实现更划算。
3. **`.env` 的真实策略**：环境变量值到底存不存？若存，是否掩码后存？预览 iframe 需要它们，则如何避免落盘与进 URL？设计稿需给出明确答案。
4. **SSE 鉴权模型**（设计稿 §10.1 + §6.3 空白）：`EventSource` 不能带 header，必须在三种方案中选一：`?token=` query / cookie / `fetch` + `ReadableStream`。这是局域网模式能否落地的前置条件。
5. **静态资源是否鉴权**：设计稿说只保护 `/api/*`，实现保护全部。需定稿，否则局域网演示场景跑不通。
6. **预览进程归属**：设计稿说 Go 用 Vite Node API 起（`preview.go`），实现改为"用户手动起 + Go 只探测端口"。**建议采纳实现的简化方案**（更符合 §10.1「不执行目标工程代码」），并改文档。
